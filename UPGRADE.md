# Upgrade and recovery

Template SemVer and upstream dependency versions are independent. The current template release is `v1.0.3`; immutable tag `v1.0.3`, compatibility channel `release-v1`, repository `tech-progress/llamaindex-durable-agents`, root `/`. Historical immutable `v1.0.1` is commit `989e904`; neither it nor `v1.0.0` may be moved. Each release needs its own exact-source/core/restore/headroom qualification; old cloud evidence is historical only. Version1.0.3 selects PostgreSQL17.11 within the same major17 without changing API dependencies, DBOS workflow/application identity or the single-slot lease contract. Quiesce writers and retain an off-volume backup before database replacement; this is not a rolling or cross-major upgrade guarantee.

This candidate changes only the recipe version, PostgreSQL 17.9 to the pinned 17.11 Bookworm index, documentation and related verification. API dependencies, Python/libpq pins, runtime notices/inventory and workflow/lease identities remain unchanged. PostgreSQL minor updates do not require a major-version migration, but that does not prove an in-place upgrade or restore for this candidate: the local verifier uses an isolated fresh database, and the parent must qualify the exact final restore path. No rolling or zero-downtime claim is added.

1. Back up the **entire dedicated PostgreSQL database**, including DBOS schema, workflow store/state/journal/events and `demo_*` tables. Keep credentials and executor prefix separately secured. Practice restoring to a disposable instance. Historical release validation restored a quiesced logical backup into a separate empty Railway volume and preserved a pending approval, original run/events and one approved ledger effect; this does not qualify `v1.0.3` or establish a production RPO/RTO.
2. Drain all runs, including approval waits, before changing workflow/event code, provider settings or DBOS application version. Alternatively keep a compatible old workflow registered and deploy new work under a deliberate new durable name and version. Do not silently reuse `invoice-approval-v1`/`approval-v1` for incompatible code.
3. Preserve `DBOS_EXECUTOR_PREFIX` and the dedicated database during ordinary same-code process replacements. Disable automatic GitHub deployments. Explicitly stop the old API deployment and confirm zero running instances before redeploying the intended `release-v1` revision; allow crash lease expiry. Stored deploy settings use one replica, zero overlap and ten-second draining, but historical Railway readiness-gated rolling replacement failed while the predecessor held the slot. Historical stop-before-replace validation with downtime recovered the original pending approval; the parent must repeat exact final candidate cloud qualification. Do not describe this as rolling or zero-downtime support.
4. Pin new versions, regenerate `uv.lock`/`bun.lock`, review upstream migrations and experimental lease changes, increment `VERSION` and `CHANGELOG.md` for distributed changes. Re-run clean image build, SQL replay, pending-approval replacement and draft audits.
5. PostgreSQL major upgrades require a documented logical restore or supported physical migration; never point a different major image at an old data directory. Preserve the mount path. Changing `POSTGRES_PASSWORD` after initialization alone does not rotate the existing database user's password.
6. Roll back application code only against a schema compatible with it and after draining new-version work. Avoid automatic downgrade migrations. Restore a backup to a separate volume first if schema rollback is required.

Exactly-once billing is not supported: a hosted proposal request interrupted before durable step persistence can be repeated after recovery. SQL ledger replay is safe because a request primary key and transactional payload check guard the actual demo effect. Extend external side effects only with a downstream idempotency contract and tested reconciliation.
